# Antithesis integration

Minimal setup to run Pyroscope in an [Antithesis](https://antithesis.com/docs/)
Kubernetes test environment. It deploys Pyroscope in v2 microservices mode,
matching production: 2 distributors, 3 segment-writers, a 3-node raft
metastore, 3 compaction-workers, 2 query-frontends, 2 query-backends, and the
small auxiliary services, with MinIO standing in for object storage. Manifests
are rendered from the production Helm chart at
`operations/pyroscope/helm/pyroscope`.

There is intentionally no test workload and no SDK assertions yet: Antithesis
starts fault injection once the deployment reports ready (the chart's
`/ready` readiness probe), and its built-in properties (crashes, hangs) apply.

The Pyroscope binary is built with Antithesis
[coverage instrumentation](https://antithesis.com/docs/reference/sdk/go/instrumentor/):
the repository's `make build/antithesis` target runs the Antithesis Go
instrumentor (a build-time source transformation — no production code is
modified) and compiles the rewritten sources with cgo enabled, as the SDK
requires. The generated symbol table ships at `/symbols` in the Pyroscope
image. The SDK and the instrumentor are `go.mod` dependencies; only the
build is affected. Notes:

- The instrumented binary is dynamically linked (the SDK loads the Antithesis
  platform library with `dlopen`), so the image uses the glibc distroless
  base instead of the production image's `distroless/static`, and it embeds
  no frontend assets.
- Files listed in `instrumentor.exclude` are compiled but not instrumented:
  the instrumentor displaces `//go:embed` directives, so every file
  containing one is excluded (see the note in that file when adding new
  `go:embed` usages).
- The build happens inside Docker under `--platform linux/amd64`; on ARM
  hosts (e.g. Apple Silicon) it runs emulated and takes considerably longer
  than a native build.

## Files

- `values.yaml` — overrides applied on top of the chart defaults: enables
  microservices mode and MinIO, disables the Alloy sub-chart, anonymous usage
  reporting, and the chart-rendered RBAC, and sizes the components to fit the
  Antithesis budget (mirroring the chart's own single-node CI sizing in
  `ci/micro-services-values.yaml`). The image reference is set at render time
  by the Makefile.
- `manifests/pyroscope.yaml` — the rendered manifests, committed for review.
  Regenerated by `make manifests` (the image reference bakes in the tenant
  registry and build tag, so regenerate with your own variables before use).
- `manifests/rbac.yaml` — static copy of the chart's discovery Role and
  RoleBinding (needed by the `kubernetes:///` metastore resolver) with
  `metadata.namespace` set explicitly, which Antithesis requires and the chart
  template omits.
- `Dockerfile.config` — the Antithesis
  [config image](https://antithesis.com/docs/getting_started/setup_guide/setup_k8s/),
  which packages `manifests/` at `/manifests`. Antithesis deploys its contents
  with `kapp` into the environment, a single-node, air-gapped K3s cluster.
- `Dockerfile.pyroscope` — the instrumented Pyroscope image: a builder stage
  runs `make build/antithesis` against the repository root (the build
  context; `Dockerfile.pyroscope.dockerignore` trims it), and the runtime
  stage mirrors `cmd/pyroscope/Dockerfile` on the glibc distroless base, with
  the symbol table at `/symbols`.
- `instrumentor.exclude` — files the Go instrumentor must not instrument
  (`//go:embed` users); compiled verbatim instead.
- `Makefile` — build and push targets, described below.
- `scripts/` — REST API clients ([reference](https://antithesis.com/docs/reference/rest_api/))
  to launch a test run (`launch.sh`), check run status (`status.sh`), and
  download run logs (`logs.sh`), plus a launch variant going through the
  [test webhook](https://antithesis.com/docs/reference/webhook/test_webhook/)
  (`webhook.sh`).

## Usage

Prerequisites: an Antithesis tenant with its registry key file and REST API
key (provided by Antithesis), plus Docker and Go (the Pyroscope binary is
built inside Docker; Go fetches helm for rendering the manifests).

```bash
cd tools/antithesis

# One-time: authenticate docker against the Antithesis registry.
make docker-login ANTITHESIS_KEY_FILE=/path/to/<tenant>.key.json

# Build the Pyroscope image from the working tree (linux/amd64) and the
# config image containing the rendered manifests.
make images ANTITHESIS_TENANT=<tenant>

# Push both images to the Antithesis registry.
make push ANTITHESIS_TENANT=<tenant>

# One-time: store the API key (and any other environment variables for the
# scripts) in a .env file, which is gitignored. Variables set in the
# environment take precedence over the file.
echo 'ANTITHESIS_API_KEY=<api key>' > .env

# Launch a test run (see --help for all options, --dry-run to inspect the
# request without launching).
./scripts/launch.sh --duration 15 --recipients 'you@example.com'

# Same, but through the test webhook, authenticating with the tenant's
# webhook username/password (ANTITHESIS_USER, ANTITHESIS_PASSWORD) instead
# of the API key.
./scripts/webhook.sh --duration 15 --recipients 'you@example.com'

# Check on a run (or list recent runs by omitting the run id).
./scripts/status.sh <run_id>

# Download a run's logs: its failure moment's logs by default, a specific
# moment with --input-hash/--vtime, or the build logs with --build.
./scripts/logs.sh <run_id>
```

The scripts talk to the REST API on `ANTITHESIS_HOST` (default
`grafanalabs.antithesis.com` — the API and web UI subdomain, independent of
the registry tenant name). The launch parameters include the config image,
the image list (the Pyroscope image built here plus the public images
referenced by the rendered manifests), and a creator name derived from
`git config user.email`.

Results appear at `https://grafanalabs.antithesis.com/runs`, and a report is
emailed to the `--recipients` (optional) when the run completes. Runs can
also be launched from `https://grafanalabs.antithesis.com/test-launchers`
(`basic_k8s_test`).

Make targets and scripts accept `IMAGE_TAG`, defaulting to the
`tools/image-tag` output (e.g. `main-fa92a887b`). Build, push, and launch
must use the same value, and the default changes with new commits or staged
changes, so pin it once for the whole sequence:
`export IMAGE_TAG=$(../../tools/image-tag)`.

## Environment constraints

The rendered manifests already satisfy the
[Antithesis Kubernetes requirements](https://antithesis.com/docs/best_practices/k8s_best_practices/),
worth keeping in mind when changing the setup:

- Everything runs on a single-node K3s cluster with no internet access. Images
  referenced in the manifests are pulled into the environment ahead of the run:
  public images can be referenced directly, private ones must live in the
  tenant registry. The `antithesis.images` launch parameter supplies additional
  images or overrides manifest image versions. Never use `latest` tags or
  `imagePullPolicy: Always` — nothing can be pulled at runtime.
- The environment is `linux/amd64`, and all images — including the config
  image — must be built for that platform. Both Makefile image targets force
  it. A host-platform config image (e.g. built on Apple Silicon) does not fail
  the run up front: the environment still boots, but the image has no
  `linux/amd64` variant, its contents never reach `/opt/config`, and setup
  fails with `kapp: Error: stat /opt/config/manifests: no such file or
  directory`.
- Total CPU requests must stay under 1 core and memory requests under 10 GiB.
  The chart's production-scale defaults request ~13 CPUs, so `values.yaml`
  carries per-component sizing (currently totalling ~630m CPU / ~1.8 GiB).
- Pyroscope component data lives in `emptyDir` volumes (chart default,
  `persistence.enabled=false`); with 3 replicas of each stateful component,
  quorum survives single-pod faults. MinIO uses two 5 Gi PVCs on the default
  `local-path` storage class.
- The bundled MinIO chart (4.1.0) offers no readiness probe hooks, so MinIO is
  the one pod without a probe; its availability is transitively enforced by
  the bucket-setup Jobs (which kapp waits on) and by the `create-bucket` init
  containers gating the distributor and segment-writer.
- Resources are rendered into the `default` namespace (`helm template -n default`,
  matching the repository's `helm/check` renders).
